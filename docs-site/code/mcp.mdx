---
title: Use Shakedown from your agent
description: Give Claude Code, Codex or any MCP client Shakedown's own MCP server, to build project files and deploy experiments from chat.
---

Shakedown serves its project operations as an MCP server. Add the server to Claude Code, Codex or another MCP client, and your agent lists, reads and writes worlds, scenarios, setups and experiments, and deploys experiments. The app's **Ask** assistant uses the same operations.

This server is separate from the MCP endpoint an agent under test gets inside a run, which holds the world's tools.

## Add the server

**Project settings → Use from an agent** shows the command for your engine.

Hosted Shakedown, with a token from **Settings → Advanced → API tokens** in `SHAKEDOWN_TOKEN`:

```bash
claude mcp add --transport http shakedown https://app.coppertide.ai/sd/mcp --header "Authorization: Bearer $SHAKEDOWN_TOKEN"
```

```toml
# Codex, ~/.codex/config.toml
[mcp_servers.shakedown]
url = "https://app.coppertide.ai/sd/mcp"
bearer_token_env_var = "SHAKEDOWN_TOKEN"
```

A local engine, over stdio, for one project folder, with `shaked` on your `PATH` (see [Self-host](/self-host)):

```bash
claude mcp add shakedown -- "$(command -v shaked)" mcp --project ~/work/my-project
```

`$(command -v shaked)` stores the full path of `shaked`, so the client starts it whatever its own `PATH` holds. Without the `PATH` step, give the path yourself: `<your clone>/core/target/release/shaked`.

`shaked mcp` works on the folder alone, with no database and no running engine. Edits work there. Deploying needs a running engine: use `POST /mcp` on the engine with an API token instead.

## The tools

| Tools | What they do | Access |
|---|---|---|
| `project_status`, `project_init`, `project_update` | The project's name, settings, counts and problems, creating a project, and changing its settings | Read, edit |
| `project_import` | Move installed benchmarks and earlier experiments into the project, showing the plan first | Edit |
| `project_example` | Add the ready example: a world on the built-in `retail` runtime, a scenario, a one-agent setup on your model key and a one-run experiment. Without `confirm`, it answers what it would write. Refused when any of its ids is taken | Edit |
| `project_import_git` | Import a repository's packages and project files from git, showing the plan first. Local engine only | Edit |
| `project_deleted`, `project_restore` | The most recent delete, and undoing a delete. Without `confirm`, `project_restore` answers the files and a `trash` name. Pass the `trash` back with `confirm: true` to restore the same delete, whatever came in between | Read, edit |
| `worlds_list`, `worlds_get`, `worlds_put`, `worlds_delete`, `worlds_dependents` | Worlds, and what uses one. Shakedown refuses a delete while a file uses the world, unless the call sends `cascade: true`. A cascade sent with `expect`, the list a preview returned, fails when the list has changed | Read, edit, delete |
| `scenarios_*`, `setups_*`, `experiments_*` | The same five for scenarios, setups and experiments | Read, edit, delete |
| `worlds_rename_group` | Move every world in a group to a new group name, showing the diff first | Edit |
| `experiments_deploy`, `experiments_runs` | Deploy an experiment, and list its deployments with each setup's results | Spend, read |
| `setups_madl` | A MADL setup's checks and its graph of agents | Read |
| `worlds_data`, `worlds_data_put`, `worlds_data_delete` | A world's data files: list and read, upload or set one JSON value, delete | Read, edit |
| `runtimes_list`, `runtimes_install`, `runtimes_check`, `runtimes_delete` | Runtime packages. Install, check and remove work on a local engine only | Read, edit |
| `analytics_summary`, `analytics_search`, `explore_*` | Figures across runs, a search of every run's steps, and Explore queries and read-only SQL. The app has no page for these | Read |

Runs, forks and compare are HTTP routes outside this server: see [HTTP API](/code/http-api).

## What agents do without asking

The token's scope bounds every call: `read` lists and reads, editing or deleting files needs `admin`, and deploying needs `run`. The project's `permissions` in `shakedown.yaml` (**Project settings → What agents may do**) set the rest:

| Setting | Values | Today |
|---|---|---|
| `edit` | `diff_first` (default): every tool taking `confirm` answers what the call changes and writes only when sent again with `confirm: true`. The tools are each `_put`, `project_update`, `project_import`, `project_restore`, `worlds_rename_group` and a delete with `cascade`. `apply_then_tell`: writes at once. | Applies to MCP clients and the assistant |
| `spend` | `always_ask` (default), or `under_cap` with a daily cap | Stored. The assistant asks before every deploy whatever the setting says, an MCP client with a `run` token deploys without a prompt, and no daily cap applies yet. |

The **Ask** assistant runs reads at once and follows `edit` for every tool taking `confirm`: a diff to apply under `diff_first`, written at once under `apply_then_tell`. Every deploy or delete becomes a card you confirm. A delete card shows the delete dialog: what uses the item, then **Delete** alone or with what uses the item. The card ignores any choice the model made. The assistant runs on your own model key, set under **Project settings → Assistant**.
