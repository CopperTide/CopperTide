Bring a system you already run into a world. Import a repository that holds Shakedown packages and project files from git, or run a Docker Compose project through the `service` integration.

## Import from git

A repository with a `shakedown.yaml` at its root and `shakedown-package.toml` packages becomes part of your project: its packages run as written, and its worlds, scenarios, setups and experiments become project items.

1. Open **Worlds** and click **Import from git**, beside **New world**.
2. Give the repository, a git URL or a path on the engine's machine, and a ref. The ref defaults to `HEAD`.
3. Click **Check**. Shakedown fetches the ref and shows the commit, the packages, each project file with what happens to it, and the repository's Compose files as candidates for the `service` integration. Nothing runs yet.
4. Click **Import**. Shakedown installs and registers the packages and writes the project files.

Import again to take a new commit. An item the last import wrote and the repository no longer has is removed, to the project's trash, so **Undo** can bring it back. Shakedown keeps the item when you edited it in the project since, when something in the project still uses it, or when another import holds it, and the plan says why. Items you made in the project, and runs, are never removed.

The repository's code runs on the engine's machine. Import from git works on a local engine. Hosted Shakedown refuses it. The same is `project.import_git` for the [MCP server](/code/mcp) and the API, and `shaked import` on the command line.

## The service integration

The `service` integration starts one Compose project per world instance, saves the volumes you list, and restores them exactly on rewind and fork. Name it in a world template or a benchmark package.

### How it works

- Shakedown starts each instance as the Compose project `shakedown_<instance>`.
- A save stops the project, archives each listed volume (owners, modes and times kept) and starts the project again.
- A start from a save makes a new project, fills its volumes from the archives and starts the project.
- Restore is exact. Approximate restore is not offered.
- The part has no tools of its own. Agents reach the services over HTTP through Shakedown's recording proxy, for the hosts you list under `http`.

The integration ran live once against a real Redis 6.2 project in Docker (save, change, restore, file owners kept). The README in `integrations/service/` has the details.

### Config

| Field | What the field holds |
|---|---|
| `compose_file` | Path of the Docker Compose file. Required. |
| `volumes` | The Compose volumes a save holds. Required. A name saves as an archive. `{name, save: postgres, service, database, user}` saves a database with `pg_dump` while the database runs. `save: hardlink` copies only changed files. `save: skip` leaves a cache empty on restore. |
| `http` | Hosts the project serves through Shakedown's proxy: `{host, service, port}` |
| `images` | The image of each Compose service, passed as `IMAGE_<SERVICE>` and kept in saves |
| `probes` | Documents read over HTTP from the services, kept in saves, for checks |
| `env` | Extra environment for `docker compose` |
| `helper_image` | An image with `tar`, used to copy volumes. Default `redis:6.2-alpine`, never pulled. |

The `postgres`, `hardlink` and `skip` strategies, `images` and `probes` passed tests against a fake Docker. The `live_service_strategies` test (Postgres, a hard-linked volume and a cache) passed once on Docker 29.1.

### Put a Compose project in a world

1. Write a world template with a system whose part is `service`, or a benchmark package whose world names a `service` part. A template system looks like this:

   ```yaml
   systems:
     - id: shop
       label: Shop
       product: Our shop (Docker Compose)
       summary: Storefront and orders with their Postgres
       required: true
       default: true
       parts:
         - {part: shop, integration: service, config: "@shop/service.yaml"}
   ```

   ```yaml
   # shop/service.yaml, next to shop/compose.yaml in the template folder
   compose_file: "{world_dir}/files/shop/compose.yaml"
   env:
     SHOP_DIR: "@shop/"   # copies the shop folder into the built world
   volumes:
     - {name: db, save: postgres, service: db, database: shop, user: shop}
     - uploads
   http:
     - {host: api.shop.internal, service: storefront, port: 8000}
   ```

2. Add the folder holding your template's folder (`<id>/template.yaml`) to `SHAKEDOWN_TEMPLATES` and start the engine.
3. Build a world from the template (**⋯ → Build a world…**). The review step lists any problems in the template before you build.
4. Name the built world as your world file's runtime package.

This example is a sketch modelled on the `software-factory` template, and nobody has run the sketch itself. A template also needs tasks, checks and instructions. The `software-factory` template in `benchmarks/world/templates/` runs three services, their Postgres databases and an observability stack this way, through `live-service`, the same program with the world clock added. Read the template's `platform/service.yaml` for a full config.
