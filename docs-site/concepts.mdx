Read this page once before you build. Every other page uses these words.

## The four files

| Item | What the file describes | Where the file lives |
|---|---|---|
| World | The systems agents work in, before any agent acts | `worlds/<id>/world.yaml` |
| Scenario | A task in one world, with disruptions, gates and checks | `scenarios/<id>.yaml` |
| Agent setup | A team to test: built-in agents, Claude Code, Codex, your code, an endpoint, or MADL | `setups/<id>.yaml` |
| Experiment | One scenario against one or more setups, with runs per setup and a budget | `experiments/<id>.yaml` |

A **project** is the folder holding these files, with `shakedown.yaml` at the root. Every file starts with a `format:` line, such as `format: shakedown-world/3`. Shakedown reads each file strictly. An unknown field, a wrong `format:` or a credential written inline counts as a problem, shown next to the item with a pointer to the value. A problem in one file never stops the rest of the project from loading.

Ids are 1 to 64 lowercase letters, digits and dashes, not starting with a dash.

## Runs, branches and steps

- A **run** is one task, one team, one world.
- A **branch** is one line of events in a run. The first branch is the original. Each fork adds a branch.
- A **step** is one recorded event: an agent start, a model call, a tool call, a handoff note, a message, a world event. Steps carry a number, `seq`.
- An **experiment** runs every setup the number of times you ask. Shakedown interleaves the setups (run 1 of every setup, then run 2) and gives run *n* of every setup the same seed, so setups meet the same conditions.

## Saves at every step

After each step writing to a part of the world, Shakedown saves the part and records the save with the step. A part of the world is one system, such as a database or a Docker Compose project. A part whose saves cost a lot declares `save_at: points` and gets saved at save points instead: before each model call through Shakedown's gateway, when a driver asks, and at the run's end.

## Rewind and fork

To **rewind**, you pick a step of an ended run. To **fork**, you change something (an agent's prompt, model, provider, kind or read-only flag) and rerun from there. Shakedown puts every part of the world back as the part stood right before the step, copies the earlier steps into the new branch, and lets the team continue.

The fork point moves back when a step cannot restart on its own. In the chain runner, the default:

- A Claude Code or Codex session cannot resume mid-way, so a fork during a CLI agent's turn starts at the start of the agent's turn.
- An API-mode agent restarts at the model call choosing the tool call.

The fork's answer and the run page say where the fork started, where you asked, and why.

## Exact and approximate restore

A fork asks for one restore mode for the whole world. Each integration declares what the integration supports.

| The part declares | Exact restore | Approximate restore |
|---|---|---|
| An exact save | From the save | From the save |
| Replay and an approximate save | Replays from the start | From the save, approximately |
| Replay only | Replays from the start | Replays from the start |
| An approximate save only | Refused, naming the part | From the save, approximately |
| Nothing | Refused | Refused |

A replay reruns every recorded input with the same seed. When a replay gives a different result from the record, the fork fails and names the step. Shakedown labels a branch restored approximately as **Approximate restore** on the run page, in the branch list and in compare.

## Scoring

When a branch ends, Shakedown saves every part and scores the world: by the named checks of the runtime package's task, or by comparing the final world with the task's expected world. Safety checks count apart from goals. A model never decides a score.
